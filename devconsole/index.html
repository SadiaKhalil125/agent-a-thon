What is real on this page?

AI wrote this

The words in each agent card (Impact, HR, Finance, Planner, Verifier) come from a real LLM call through the configured provider. A full run makes 7 calls. If the model is down, the step shows "failed" and nothing is invented.

Computed by code

Every number (completion day, cost, deadline met, conflicts) comes from the deterministic solver, never from the AI. The Verifier's approve or reject decision also comes from the solver; the AI only writes the reason.

Simulated data

The company, people, projects, invoices and the HRIS / tracker / ERP / CRM / calendar connectors are fabricated and in-process. No real system is contacted.

1 Pick a scenario

Each card is an event "arriving" from a connected system. Three are disruptions (someone is out); the CRM one is a client meeting where Business Development logs new work and Sales, HR and Finance read the same record. The same five agents handle both kinds.

2 Run the AI agents

Impact first, then HR and Finance in parallel, then the Planner proposes plans, then the Verifier checks them. If the Verifier rejects a plan, the Planner revises once.

3 Compare the plans

All numbers here are Computed by code. "verified" means the plan is feasible (no double-booking or other conflicts); it can still miss a deadline, so compare the Deadlines column. "rejected" means unsafe, so it cannot be approved. The coloured bars show who works on what, by working day.

Run the agents to see plans.

4 Approve and check the outcome

Approving applies the plan to the twin (/api/execute), then the engine compares the result with what the plan promised (/api/outcome). Try approving the rejected plan: the engine must refuse.

Run the agents, then press "Approve" on a plan.

5 Automatic self-checks (no AI calls, free)

Quick API checks against the rules in docs/contracts.md: approval gate (including the client-meeting scenario), tampering, size limits, security headers, passcode, simulated connectors.

Scope: what works today and what does not

ScenariosFour, defined in the seed. Three are disruptions (developer out days 1 to 5, out days 1 to 3, out and contractor late). The fourth is a client meeting: Business Development logs a new 5-day Loyalty API add-on in the CRM and the same agents decide whether Northstar can say yes. There is no form for a free-form event yet; the API refuses unknown scenario ids. The engine itself accepts other "person unavailable on days X to Y" windows (tested at engine level).
CompanyOne fabricated company, Northstar Systems: 4 people, 3 tasks, 2 projects, 1 invoice. The client-meeting scenario adds a third project, task, commitment and invoice inside that scenario only. No real or uploaded data.
Plan optionsAlways the same three strategies (wait or queue, reassign to the backup person, bring in the contractor) plus one revision of the backup, applied to the first task the event touches (or the new work). If nobody else is qualified the engine refuses honestly instead of guessing.
DepartmentsNo separate Sales or BD agent. The meeting record (who logged it, what was asked, the quoted value, who it is shared with) is data the existing Impact, HR/Resource and Finance agents read.
AIReal LLM for the five agent steps; the numbers and the verdict are code. In automated tests the model is replaced by a scripted fake, so tests never call a real model.
ConnectorsSimulated (read-only). No webhooks, write actions, audit log or Action Center yet.
DeploymentWorks locally. Not yet deployed to Vercel.
